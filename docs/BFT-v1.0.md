## **5\. Пользовательский сценарий верхнего уровня**

Установка → онбординг → переход в главное меню → выбор традиции или «собрать свой набор» → сборка модулей → регулярное использование.

Дашборд (кнопка “Практика”): сегодняшние особые дни, текущие трекеры, чтение дня.

Повседневное использование: сверил календарь (упосатха/10-25/праздник), нажал счёт в трекере, прочитал чтение дня.

Практика без сети и без регистрации; данные живут только на устройстве, с возможностью работы в онлайн.

Критичные UX-сценарии исследованы в CJM онбординга (UX/UX-исследование.md, раздел 6).

## **8\. UX-требования**

Источник: UX/UX-исследование.md — анализ 13 конкурентов, персоны, CJM, UI-паттерны.

### **8.1 Принципы дизайна продукта**

| ID | Принцип | Обоснование |
| :---- | :---- | :---- |
| **UX-A-1** | **Спроектировано для практики, не для соревновательного вовлечения**: без streak-механик, бейджей, соревнований | Референс Bodhi Tree (Buddhist Calendar). Практика — не геймификация |
| **UX-A-2** | **Тишина и спокойствие**: низкая стимульная нагрузка, никаких «срочных» пушей | Аудитория: медитирующие, аскетичные традиции |
| **UX-A-3** | **Прозрачность и приватность**: «ничего не продаём, не следим» | D-6, обещание на онбординге |
| **UX-A-4** | **Точность важнее красоты**: календарные даты непротиворечивы (урок Norbu: лунный день «сбит на день» — репутационные риски) | NFR-CAL-5, R-5 |
| **UX-A-5** | **Минимум трения онбординга**: 1 решение (традиция/набор), дальше настроено по умолчанию | CJM онбординга |
| **UX-A-6** | **Один функция — один экран** (мобильный сценарий) | Паттерн из опросника проекта |

### **8.2 Требования к состояниям экрана**

·         Пустое состояние списка трекеров: объяснение \+ действие «Создать» (не «нет данных»).  
·         Загрузка: скелетоны/спиннер не дольше фронт-секунд; оффлайн-режим без сетевых ошибок.  
·         Ошибка календаря (если непроверенный день): честное «дата пока не проверена», не «нет праздника».  
·         Смена традиции: подтверждение, что данные не потеряются (FR-ONB-4).

### **8.3 Критические CJM-сценарии (этапы онбординга)**

Открытие → за 10 должно быть секунд понятно, что это и для кого.

Выбор традиции: школа должна быть узнаваема без глубоких знаний.

Сборка: пользователь видит итоговый набор модулей и может «разобрать как использовать».

Первый день использования: дашборд (кнопка “Практика”) показывает что-то полезное сразу.

## **12\. Требования к архитектуре**

·         Модульность: ядро не знает о школах; запрещены импорты между features (guard-тесты).  
·         Модули общаются через event bus (D-7) или DI (Riverpod, D-4).  
·         Конфигурируемость через пресеты (не хардкод); AOT — рантайм-плагины невозможны (D-5).  
·         События — низкоуровневый транспорт; Riverpod — состояние UI (D-7).  
·         Архguard: analyze 0 \+ тесты зелёные \+ CI зелёный — условие приёмки этапа (ROADMAP).
