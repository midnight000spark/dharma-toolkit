# Миграции БД

Правила изменения схемы SQLite. Введены на подэтапе 5.0.1 для закрытия R-7 и R-8.

## Инвариант

**Каждая версия схемы имеет свою ветку миграции. Отсутствие ветки — ошибка,
а не повод ничего не делать.**

До 5.0.1 `onUpgrade` выглядел так:

```dart
onUpgrade: (Migrator m, int from, int to) async {
  if (from < 2) {
    await m.createAll();
  }
}
```

Здесь два дефекта. Во-первых, при `schemaVersion == 3` переход 2 → 3 не выполнял
**ничего**: не ошибка, не потеря данных, а тишина — и «no such table» у пользователя
в рантайме. Во-вторых, `createAll()` не изменяет уже существующие таблицы,
поэтому добавить колонку им нельзя в принципе.

Сейчас переходы применяются по одному, а неизвестная версия бросает `StateError`
при первом же открытии базы — то есть на машине разработчика, а не у пользователя.

## Как добавить версию схемы

1. **Изменить таблицы** в `lib/features/*/data/*_tables.dart` или
   `lib/core/db/app_database.dart`.
2. **Перегенерировать код**:
   ```bash
   dart run build_runner build --delete-conflicting-outputs
   ```
3. **Увеличить `schemaVersion`** на единицу в `lib/core/db/app_database.dart`.
4. **Добавить ветку** в `AppDatabase._migrateToVersion`:
   ```dart
   case 3:
     await m.addColumn(practices, practices.presetPracticeId);
     break;
   ```
   Новая таблица — `m.createTable(...)`. Новая колонка — `m.addColumn(...)`.
   `createAll()` в ветках миграции использовать нельзя.
5. **Добавить тест перехода** в `test/core/db/migration_test.dart`:
   создать базу предыдущей версии подклассом с зафиксированным `schemaVersion`,
   записать в неё данные, открыть актуальной версией, проверить и новую схему,
   и сохранность данных.
6. **Прогнать тесты**: `flutter test test/core/db/migration_test.dart`.

Пропустить шаг 4 молча нельзя: без ветки тест
«объявленная, но нереализованная версия падает громко» покраснеет.

## Чек-лист ветки миграции

Ветка обязана пройти все пять пунктов, иначе она не принята:

- [ ] **Тест перехода** (шаг 5 выше) — с пользовательскими данными на входе,
      а не с чистой базой. Данные снимаются с фикстуры предыдущей версии,
      а не с текущей схемы.
- [ ] **Бэкфилл**, если новая колонка участвует в уникальности или в upsert-
      ключе: `NULL` у существующих строк = невидимость для upsert и расщепление
      данных. Либо — как выбрано в C4/D-45 — **доказанная пустота популяции**
      с границей на слое записи: ветка миграции, которая на всех реальных базах
      делает no-op, хуже инварианта, делающего состояние недостижимым.
      Угадывать значение по имени (`name`) нельзя: одноимённая пользовательская
      строка получает чужой стабильный id, и её счёт и `target` уезжают в
      пресетную запись (красный тест «бэкфилл по имени поглотил бы
      пользовательский счёт»).
- [ ] **Атомарность**: цепочка версий применяется одной транзакцией
      (`transaction(...)` внутри `onUpgrade`, W6). Личная идемпотентность
      шага — не замена транзакции, а страховка на случай, если ветку придётся
      повторить поверх уже частично мигрированной базы (такие базы могли
      появиться до W6).
- [ ] **Повторно-безопасность**: ветка должна выдерживать второй прогон поверх
      своей же работы (`_hasColumn`, `IF NOT EXISTS`, `CREATE ... IF NOT EXISTS`).
      Гард атомарности (`цепочка миграций атомарна`) проверяет, что сбой на
      середине не оставляет частично новой схемы при старом `user_version`.
- [ ] **Единицы и семантика значений**: там, где ветка трогает данные, сверка
      с тем, что реально пишет drift (см. «Историческая фикстура v2» ниже) —
      DateTime-колонка это секунды, а не миллисекунды.

## Ограничения SQLite

`ALTER TABLE` в SQLite умеет немногое. Прямо поддерживаются:

- добавление колонки (`m.addColumn`) — только nullable или с `DEFAULT`;
- переименование таблицы и колонки (`m.renameColumn`).

Всё остальное — смена типа, добавление `NOT NULL` без значения по умолчанию,
добавление внешнего ключа, изменение первичного ключа — требует пересоздания
таблицы: создать новую, перелить данные, удалить старую, переименовать.
В Drift для этого есть `m.alterTable(TableMigration(...))`.

Это прямо касается B-11: чтобы добавить `ON DELETE CASCADE` к `count_history`,
понадобится именно пересоздание таблицы, а не `addColumn`.

## Что покрыто тестами, а что нет

`test/core/db/migration_test.dart`, 18 тестов:

| Тест | Что проверяет |
|---|---|
| свежая установка | `onCreate` создаёт все таблицы, `user_version` = `schemaVersion` |
| апгрейд 1 → 2 | таблицы трекера создаются, **строка в `presets` переживает миграцию** |
| работа после апгрейда | в мигрированную базу можно писать — схема создана целиком, а не по именам |
| колонки `practices` | набор колонок соответствует объявленному |
| апгрейд 2 → 3 | колонка `preset_practice_id`, индекс B-3, каскад B-11 — при сохранности счёта и истории |
| апгрейд 3 → 4 | таблица настроек уведомлений, данные целы, пустая таблица — штатное состояние |
| уникальный индекс (B-3) | дубль пресетной практики запрещён, `NULL` (кастомные) и другая традиция — свободны |
| нереализованная версия | `schemaVersion` без ветки миграции роняет открытие базы (регрессия на R-8) |
| препосылка downgrade | старая версия ровно на 1 ниже текущей (не даёт downgrade-тесту протхнуть проверку) |
| downgrade | `from > to` бросает `StateError` с направлением перехода и **не портит файл** (B-12) |
| атомарность цепочки (W6) | сбой перед последней веткой откатывает схему к исходной версии; следующий прогон мигрирует до конца |
| FK на тест-пути (W7) | `forTesting(NativeDatabase.memory())` без `setup:` получает `foreign_keys = ON` и каскад B-11 |
| FK на прод-пути (W7) | `NativeDatabase(file, setup: enableForeignKeys)`: pragma ON, сирота в `count_history` отбит, каскад работает |
| фикстура v2 (W27) | снимок генератора replay-ится в базу; единицы времени — секунды, значения читает drift-маппинг |
| почти-реальная legacy-база (C4/D-45) | переход v2 → текущая сохраняет счёт и историю, инвариант `preset_id ⇒ preset_practice_id` не нарушен |
| applyPreset дважды после миграции (C4) | число строк стабильно, кастомная строка не затронута, популяции C4 нет |
| отказ от бэкфилла по имени (D-45) | одноимённые кастомная и пресетная строки сосуществуют, счёт 21 000 остаётся на своей |
| второй прогон цепочки (W6) | `user_version` откатан без изменения схемы: ветки проходятся заново, история не удваивается, индекс и каскад целы |

**Раньше значилось «не покрыто» — теперь покрыто** (W26: документ противоречил
коду; сверено с `lib/core/db/app_database.dart`):

- **Понижение версии** — покрыто двумя тестами (препосылка + `StateError` и
  сохранность файла), с 5b.
- **Целостность внешних ключей** — `PRAGMA foreign_keys = ON` применяется
  в `migration.beforeOpen` на **любом** исполнителе (W7); дубль `setup:
  enableForeignKeys` на прод-соединении оставлен намеренно: он включает FK до
  начала миграций, а хук drift вызывается после них.

**Действительно не покрыто:**

- **Повреждение файла БД** (битые страницы, обрезанный файл): ни `PRAGMA
  quick_check`, ни fallback на `destructive` нет — отказ всплывает текстом на
  экране списка, а не на экране восстановления (C1(2), пакет FIX-1 блок 5).
- **Реальная пользовательская база** как вход миграции: переходы проверяются на
  фикстурах из снимка схемы. С живого файла (эмулятор, `adb pull
  app_flutter/dharma_toolkit.sqlite`, `user_version = 4`) сверено только то, что
  в него можно положить руками: инвариант C4 (0 строк `preset_id` без
  `preset_practice_id`) и то, что `created_at` там — секунды. Полноценного
  прогона миграций на скопированной пользовательской базе нет: v2-файлов у
  устройства не бывало (пишущего кода на v2 не было), даунгрейдить v4-файл до v2
  — значит тестировать схему, которой никто не видел.
- **Отказ в середине прикладной материализации** (`applyPreset` пишет в три
  хранилища без атомарности, W14) — это не миграция схемы, но тот же класс
  «незавершённый переход».

## Историческая фикстура v2

`test/fixtures/schema_v2_drift.sql` — DDL версии 2, **эмитированный генератором
drift**, а не переписанный руками. Рукописная фикстура (`_AppDatabaseV2Raw` до
FIX-1) отличалась от генератора в двух местах: `DEFAULT 1725000000` вместо
`DEFAULT (CAST(strftime('%s', CURRENT_TIMESTAMP) AS INTEGER))` и
`ON DELETE RESTRICT`, которого генератор на v2 не выдавал (там просто
`REFERENCES practices (id)` — то есть NO ACTION).

Как снять заново (для любой исторической версии):

```bash
mkdir -p /tmp/rev && git archive <ревизия-нужной-версии-схемы> | tar -x -C /tmp/rev
cd /tmp/rev && flutter pub get        # lock той ревизии, не текущего дерева
# тест: AppDatabase.forTesting(NativeDatabase.memory()) → первый запрос →
#   SELECT type, name, sql FROM sqlite_master WHERE sql IS NOT NULL ORDER BY rowid
```

Анкоры: `f0b6c5e` — версия 2 (`practices` + `count_history`), `e209bdf` —
версия 1 (только `presets`). Из дампа исключается `sqlite_sequence` — её SQLite
создаёт сам под AUTOINCREMENT.

### Единицы времени в DateTime-колонках — секунды

**[ФАКТ, проверено прогоном и исходником drift 2.34.3 (MIT)]**: целочисленные
DateTime-колонки drift хранит как **число секунд** с эпохи — `mapToSql` делает
`millisecondsSinceEpoch ~/ 1000`, а `currentDateAndTime` в DDL — это
`CAST(strftime('%s', CURRENT_TIMESTAMP) AS INTEGER)`. Точность — до секунды.

Это опровергает встречавшееся в ревью утверждение, что «drift пишет
`currentDateAndTime` в миллисекундах» (W27): из него следовала «починка»
фикстуры умножением на 1000, и она была бы регрессией. Гард — тест
«фикстура v2 — DDL генератора, единицы времени — секунды»: он краснеет, если в
снимок закрадываются миллисекунды (проверено мутацией `* 1000` в файле-снимке:
`Expected: a value less than <60> / Actual: <1788062979168>`).

## Почему не `stepByStep`

Ревью 5.0 предлагало перейти на `stepByStep` — генерируемые Drift миграции
по снимкам схемы. Это по-прежнему правильная цель, но она требует запуска
генератора, а на момент реализации 5.0.1 тулчейн Dart/Flutter был недоступен,
и сгенерированные файлы (`drift_schemas/*.json`, `schema_versions.dart`) создать
было нечем. Ссылаться из `lib/` на несуществующий сгенерированный файл нельзя —
проект перестал бы собираться.

Поэтому 5.0.1 закрывает существо R-7 и R-8 вручную написанными миграциями.
См. D-17 в `STATE.md`.

Ручные миграции и `stepByStep` не конфликтуют: второе — генератор того же
`onUpgrade`. Переход выполняется заменой тела `onUpgrade` и ничего не ломает.

**Что показала проверка в FIX-1 (2026-09-19).** Генератор снимков доступен —
`dart run drift_dev schema dump lib/core/db/app_database.dart <папка>` работает и
на текущем пине. Но в формате снимка `_meta.version: 1.3.0` лежит **модель
схемы** (список колонок и констрейнтов), а не DDL: у таблиц нет `createStmt`,
у индексов `sql: null`. Общедоступного читателя, который превращает снимок
обратно в `CREATE TABLE`, в пине нет — `package:drift/dev_apis.dart`
(`MigrationUtils.createConstructFromSchemaStatements`) в drift 2.34.3
отсутствует, а `SchemaReader` живёт во внутренностях `drift_dev/lib/src` и
наружу не экспортируется. То есть переход на `stepByStep` — это либо апгрейд
стека, либо собственный DDL-эмитер (рукописный, ровно тот класс дефекта,
который W27 лечит). Пока это так, исторические схемы снимают прогоном
соответствующей ревизии (см. «Историческая фикстура v2»).

### Как перейти, когда тулчейн доступен

```bash
dart run drift_dev make-migrations
```

Команда создаёт снимки схемы в `drift_schemas/`, файл шагов и заготовки тестов.
Проверить перед принятием:

- снимки должны существовать **для каждой** версии, включая исторические 1 и 2.
  Версия 1 — это только таблица `presets` (коммит `f0b6c5e~1`), версия 2 добавила
  `practices` и `count_history` (коммит `f0b6c5e`). Чтобы получить снимок v1,
  снимок нужно сгенерировать на исторической ревизии;
- ручные тесты из `migration_test.dart` не удалять: они проверяют **сохранность
  пользовательских данных**, а генерируемые проверяют только совпадение схемы.

Зафиксированы в `pubspec.lock` на 2026-08-31, сверено с закоммиченным локом
после откатa дрейфа (C10, пакет FIX-1, 2026-09-19):
