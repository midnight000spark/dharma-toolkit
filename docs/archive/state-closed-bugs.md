### B-1: список трекеров не обновляется после инкремента
- **Описание**: Riverpod FutureProvider не инвалидируется после изменения данных в БД
- **Влияние**: пользователь не видит обновлённый счёт без перезапуска экрана
- **Решение**: D-16 (перевод на Drift .watch())
- **Уточнение (2026-08-31)**: причина не в отсутствии инвалидации, а в том, что `practiceListProvider` — `FutureProvider.autoDispose.family` (`practice_provider.dart:8-13`), а экран списка остаётся смонтированным под `context.push`, поэтому autoDispose не срабатывает. Инвалидация в коде есть, но только после `/create` (`practice_list_screen.dart:41-43`); после экрана счёта её нет. D-16 верно. Замечание к реализации: `.watch()` требует нового метода в репозитории (`watchByTradition`), то есть трогает слой данных, а не только провайдер.
- **Статус**: закрыт (5.0.3, 2026-09-01) — `practiceListProvider` переведён на `StreamProvider.family`, `watchByTradition` в репозитории, экран списка обновляется автоматически через стрим. Подтверждено ручным прогоном и поведенческим тестом.
- **Приоритет**: высокий (блокирует нормальное использование)

### B-2: прогресс не ограничен 100% в UI
- **Описание**: LinearProgressIndicator показывает 1666% когда currentCount > target
- **Влияние**: визуальный баг, ломает UX
- **Решение**: ограничить значение progress в UI (min(progress, 1.0))
- **Уточнение (2026-08-31)**: чинить надо не в UI, а в домене — источник это геттер `PracticeEntity.progress` (`practice.dart:45-48`). Проявлений уже два: `LinearProgressIndicator` (`practice_count_screen.dart:66-68`) и «1666%» в списке (`practice_list_screen.dart:30`); при UI-фиксе клампить придётся ещё в дашборде (SCR-7), истории (SCR-9) и виджете домашнего экрана. **Клампить прогресс, но не счёт**: практикующий перевалит за 100 000 повторений, и обрезать `currentCount` было бы враньём о его практике. `progress` → `clamp(0, 1)`, рядом `rawProgress` для «цель достигнута, 112%». Дополнительно: `target` не валидируется, отрицательная цель даёт отрицательный прогресс; тестов на >100% нет.
- **Статус**: закрыт (5.0.4, 2026-09-01) — кламп в домене (`progress = clamp(rawProgress,0,1)`, невалидная цель → 0.0), `rawProgress` для перевыполнения, `copyWith`; UI не клампит счёт. 8 доменных тестов; мутация (снятие clamp) → тест 150/100 красный. Ручной прогон пользователя: трекер с целью 10, накликано 15 → 100%; нёндро 10 000 доведён до 100% и работает
- **Приоритет**: средний (косметический)

### B-5: ошибка инициализации даёт чёрный экран без пути восстановления
- **Описание**: `ConfigModule._loadPreset` (`config_module.dart:43-45`) перебрасывает любое исключение как `StateError`; оно поднимается через `registry.initAll()` (`main.dart:32`) **до** `runApp()` (`main.dart:39`). Нет `runZonedGuarded`, `FlutterError.onError`, `ErrorWidget.builder`. Триггеры: повреждённый JSON, битый файл SQLite, отказ `path_provider`, неудачная миграция.
- **Влияние**: для offline-first без бэкенда и аккаунтов (D-6) локальное состояние — единственное; падение на старте = кирпич.
- **Решение**: обернуть инициализацию, экран восстановления («не удалось прочитать данные» + «сбросить настройки»); модули деградируют поодиночке, а не валят процесс.
- **Статус**: закрыт (5.0.4, 2026-09-01) — `initAll` собирает `ModuleInitReport`, критичные модули (database/storage/config/preset_manager) → `RecoveryApp`, остальные деградируют с логом; `runZonedGuarded` + `FlutterError.onError` + `ErrorWidget.builder` (человекочитаемо). Сброс — только через диалог подтверждения (I-3: не resetPreset). 2 recovery-теста + тест реестра. Ручной прогон пользователя: повреждённый файл БД → «Не удалось прочитать данные», обе кнопки работают, сброс вернул к выбору пресета
- **Приоритет**: блокер

### B-8: гонка при быстром тапе «+»
- **Описание**: `_increment` (`practice_count_screen.dart:36-40`) не защищён от повторного входа: каждый тап запускает `incrementCount` и следом `_loadPractice`, порядок завершения чтений не гарантирован — счётчик может «прыгнуть назад».
- **Влияние**: высокое. БФТ описывает целевой сценарий буквально как быстрый многократный тап (счёт мантр на ходу, крупная кнопка, нёндро 100 000) — это основной режим работы, а не edge case.
- **Решение**: `.watch()` вместо ручной перезагрузки (снимается вместе с B-1/B-6) + инкремент одним `UPDATE ... SET current_count = current_count + ?` вместо read-modify-write (`practice_repository.dart:46-71`). Отдельно: кнопки `+1/+10/+100` — обычные `ElevatedButton` в `Row`, а SCR-9 требует крупную кнопку «+».
- **Статус**: закрыт (5.0.3, 2026-09-01) — атомарный `UPDATE` через `PracticesCompanion.custom` (F-36), экран на `StreamProvider` (убрал read-modify-write). Мутационная самопроверка: read-modify-write без транзакции даёт 1 вместо 2 при параллельных инкрементах — тест краснеет. Подтверждено ручным прогоном (5 быстрых тапов) и поведенческим тестом.
- **Приоритет**: высокий

### B-9: форма создания — двойное создание, пробелы вместо имени, потерянная цель
- **Описание**: `create_practice_screen.dart:31-52` — кнопка не блокируется на время `await create(...)` (двойной тап = две практики); валидатор проверяет `value?.isEmpty` вместо `trim().isEmpty` (строка 69), имя из пробелов проходит; `int.tryParse` (строка 39) молча вернёт `null` для «100 000» с пробелом или «abc» — цель теряется без сообщения, отрицательные проходят; единица измерения пишется через `onChanged` без контроллера и без `trim`.
- **Влияние**: дубли в БД и потеря введённых данных без обратной связи.
- **Причина живучести**: три теста экрана проверяют только валидацию пустого имени и ввод текста в поля — путь сохранения не покрыт ни одним тестом.
- **Решение**: блокировка кнопки на время сохранения, `trim`, валидатор для цели, тесты на путь сохранения.
- **Статус**: закрыт (5.0.4, 2026-09-01) — `_saving`-гард + disabled-кнопка, trim имени/единицы, парсинг цели с группировкой и видимой ошибкой; 6 тестов пути сохранения на Completer-двойнике (урок 5); мутация (снятие блокировки) → тест двойного тапа красный. Ручной прогон пользователя: имя из пробелов → ошибка; «-5» → ошибка; «100 000» → создалось с целью 100000; двойной тап → один трекер
- **Приоритет**: высокий

### B-10: create() молча выбрасывает createdAt и updatedAt
- **Описание**: `PracticeEntity` требует оба поля как `required`, `PracticesCompanion.insert` их принимает (`app_database.g.dart:725-738`), но `practice_repository.dart:32-42` их не передаёт — берутся дефолты БД. Весь вызывающий код (`DevSeeder`, форма создания, все тесты) вычисляет `final now = DateTime.now()`, и это значение выбрасывается.
- **Влияние**: при массовой вставке практик из пресета (B-3) все строки получат один timestamp с точностью до секунды, а список сортируется `orderBy(createdAt)` — порядок трекеров станет недетерминированным. Дальше — импорт бэкапа (бэклог v1.1), где чужие даты обязаны сохраняться.
- **Решение**: передавать оба поля в companion.
- **Статус**: закрыт (5.0.4, 2026-09-01) — `create()` прокидывает `createdAt/updatedAt`; тесты: точные даты сохраняются, порядок `getByTradition` по createdAt детерминирован (разнос 2с по I-6). Визуально из UI не проверяется — гарантия репозиторными тестами
- **Приоритет**: высокий

### B-17: DST-таймзоны сдвигают конец диапазона упосатх (быв. L6)
- **Описание**: `uposatha_calendar_provider.dart:54` — `span = b.difference(a).inDays + 1`; продукт фиксирован на ru-локаль, но таймзона устройства произвольна — на переходах DST конец диапазона сдвигается на день.
- **Влияние**: пропущенный/лишний день на границе окна в экзотических таймзонах.
- **Решение**: цикл `while (!d.isAfter(b))` вместо счётчика дней.

  тест детерминирован на DST-отсутствующих хостах (Moscow без DST с 2014, CI

  до фикса красным: новолуние 08.04 терялось из окна 25.03–08.04 через

- **Приоритет**: низкий
