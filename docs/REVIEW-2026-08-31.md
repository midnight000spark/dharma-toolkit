**Дата**: 2026-08-31

## Как это проверялось и чего я не делал

Все находки получены **статическим чтением кода**. Flutter и Dart в среде ревью
не были установлены — `flutter analyze` и `flutter test` не запускались.
Заявленные «49 тестов зелёные, analyze 0» не подтверждались и не опровергались.

Пункты, зависящие от поведения конкретной версии пакета (Drift, go_router),
отмечены отдельно — их стоит перепроверить запуском.

## Вердикт

Ядро собрано аккуратно. Проблема не в качестве кода, а в **разрыве между
документами и кодом**: три требования помечены «сделано», а в коде их нет;
вся система пресетов не подключена к работающему приложению; единственный
источник трекеров — `DevSeeder`, помеченный на удаление в Этапе 8.

Общее у всех блокеров: **этап отмечен ✅, но его критерий выхода не выполняется.**
Это не «недоделки на потом», а уже принятые как закрытые обязательства.

Рекомендация: Этап 5 открывать не с календаря, а с подэтапа 5.0.

# Блокеры

## B-3 — пресетные трекеры не создаются вообще (FR-TRK-3 не реализован)

Поле `PresetSchema.practices` нигде в `lib/` не читается:

```bash
grep -rn "\.practices" lib/    # только объявление в схеме + обращения к таблице practices
```

`PresetManager.applyPreset` (`preset_manager.dart:43-58`) пишет только строку
в таблицу `presets`. Единственный источник трекеров — `DevSeeder`
(`dev_seeder.dart:11-51`), который захардкожен, работает только под `kDebugMode`
(`main.dart:35-37`) и сам помечен `TODO: удалить в Этапе 8`.

**Следствие**: release-сборка Этапа 9 стартует с пустым списком практик.
П1 из БФТ (нёндро, 100 000 повторений) не может начать пользоваться приложением.

**Ломает**: критерий выхода Этапа 3 («применение пресета создаёт записи в БД»)
и Этапа 4 («пресетный трекер считает»). Оба отмечены ✅.

**Нюанс починки**: в таблице `Practices` есть `presetId`, но **нет колонки под
стабильный id практики из пресета**. Без неё повторный `applyPreset` будет
плодить дубли. Значит, нужна миграция — идёт в один пакет с R-8.

## B-4 — вся система пресетов недостижима из работающего приложения

`applyPreset`, `switchPreset`, `resetPreset`, `getPreset`, `allPresets`
не вызываются нигде в `lib/` — только из тестов. Модуль полностью покрыт
юнит-тестами и полностью отключён от UI.

- `ConfigModule` грузит ровно один файл `sample.json` (`config_module.dart:26-30`)
- `presets/tree.json` (дерево школ из D-11) **не читает никто** — мёртвый ассет,
  при этом закрывающий FR-PRS-4 галочкой
- `traditionTag` захардкожен литералом `'sample'` в `router.dart:13,17`

**Следствие**: FR-ONB-4 («смена традиции без потери данных») физически не может
работать. Изоляция по традиции (FR-TRK-8) есть в репозитории и обнулена на экране.

**Фикс**: `traditionTag` должен приходить из `PresetManager.activePreset` через
провайдер. Это же снимает половину работы Этапа 8.

## B-5 — любая ошибка инициализации даёт чёрный экран

`ConfigModule._loadPreset` (`config_module.dart:43-45`) ловит любое исключение
и перебрасывает как `StateError`. Оно поднимается через `registry.initAll()`
**до** `runApp()`:

```dart
// main.dart:32
await registry.initAll();   // кидает — и runApp() ниже не будет
// main.dart:39
runApp(const ProviderScope(child: DharmaToolkitApp()));
```

Нет ни `runZonedGuarded`, ни `FlutterError.onError`, ни `ErrorWidget.builder`.
Триггеры реальны: повреждённый JSON, битый файл SQLite, отказ `path_provider`,
неудачная миграция.

**Почему блокер**: для offline-first приложения без бэкенда и аккаунтов (D-6)
локальное состояние — единственное состояние. Падение на старте = кирпич
без пути восстановления.

**Фикс**: обернуть инициализацию, при провале рисовать экран восстановления
(«не удалось прочитать данные» + «сбросить настройки»). Модули должны
деградировать поодиночке, а не валить процесс.

## R-8 — миграции: начиная с версии 3 `onUpgrade` молча ничего не делает

Формулировка R-7 верна, но недооценивает проблему тремя способами:

```dart
// app_database.dart:62-66
onUpgrade: (Migrator m, int from, int to) async {
  if (from < 2) {
    await m.createAll();
  }
}
```

1. **Ветки для `from == 2` нет.** Этапы 5–7 добавляют таблицы, `schemaVersion`
   станет 3 — апгрейд 2→3 не выполнит *ничего*. Не ошибка и не потеря данных:
   тишина, а потом «no such table» в рантайме у пользователя.
2. **`createAll()` не добавляет колонки** в существующие таблицы (нужен
   `m.addColumn`). А B-3 требует именно новой колонки в `practices`.
3. **Нет тестов миграций**: не сгенерированы дампы схемы, значит нет способа
   проверить переход между версиями иначе как вручную на устройстве.

**Фикс**: `stepByStep`, дампы схемы в `drift_schemas/`, генерируемые тесты
миграций. Единственный пункт отчёта, который дешевле сделать сейчас,
чем когда у беты появятся живые базы.

# Баги трекера

## B-1 — список не обновляется (подтверждён, диагноз уточнён)

`practiceListProvider` — это `FutureProvider.autoDispose.family`
(`practice_provider.dart:8-13`). При `context.push('/practice/:id')` экран списка
**остаётся смонтированным** под новым маршрутом, поэтому `autoDispose`
не срабатывает и кэш не сбрасывается.

Уточнение к записи в STATE.md: инвалидация в коде **есть**, но только после
`/create` (`practice_list_screen.dart:41-43`). После экрана счёта её нет.
Точечный `invalidate` тут в принципе не лечит — путей изменения данных будет
всё больше (дашборд SCR-7, история SCR-9, применение пресета).

**D-16 верно.** Уточнение: переход на `.watch()` требует нового метода
в репозитории (`watchByTradition`), то есть трогает слой данных, а не только провайдер.

## B-2 — прогресс > 100% (подтверждён, чинить надо не в UI)

Источник — геттер в доменной модели, а не виджет:

```dart
// practice.dart:45-48
double get progress {
  if (target == null || target == 0) return 0.0;
  return currentCount / target!;      // ничем не ограничен
}
```

Проявляется в двух местах: `LinearProgressIndicator`
(`practice_count_screen.dart:66-68`) и текст «1666%» (`practice_list_screen.dart:30`).

STATE.md предлагает «ограничить значение в UI» — тогда клампить придётся
и в дашборде, и в истории, и в виджете домашнего экрана. Каждое новое место —
новый шанс забыть.

**Продуктовый нюанс**: клампить нужно прогресс, но **не счёт**. Практикующий
спокойно перевалит за 100 000 простираний, и обрезать `currentCount` было бы
враньём о его практике. Правильно: `progress` возвращает `clamp(0, 1)`,
рядом живёт `rawProgress` для «цель достигнута, 112%».

Дополнительно: `target` нигде не валидируется, отрицательная цель даёт
отрицательный прогресс. Тестов на >100% нет ни одного.

## B-6 — вечный спиннер и `setState` после `dispose`

```dart
// practice_count_screen.dart:27-34
Future<void> _loadPractice() async {
  final repository = ref.read(practiceRepositoryProvider);
  final practice = await repository.getById(widget.practiceId);
  setState(() {                       // нет проверки mounted
    _practice = practice;
    _loading = false;                 // при исключении не выполнится никогда
  });
}
```

- Ушли назад во время загрузки — `setState` на размонтированном стейте.
- `getById` использует `.getSingle()` (`practice_repository.dart:23-28`),
  который **кидает** при отсутствии строки. `try/catch` нет, поэтому `_loading`
  навсегда `true` — экран показывает спиннер, и на нём нет ни AppBar,
  ни кнопки «Назад».

**Триггеры**: deep link `/practice/999` (deep linking заявлен как преимущество
go_router в F-17), удалённая практика, будущая смена пресета.

## B-7 — роутер падает на нечисловом id

```dart
// router.dart:22
final id = int.parse(state.pathParameters['id']!);   // FormatException на /practice/abc
```

У `GoRouter` не задан `errorBuilder`. Пара к B-6: вместе они означают,
что **ни один** некорректный маршрут не обрабатывается.

**Фикс**: `int.tryParse` + редирект на список, плюс `errorBuilder` на роутере.

## B-8 — гонка при быстром тапе «+»

`_increment` (`practice_count_screen.dart:36-40`) не защищён от повторного входа:
каждый тап запускает `incrementCount`, а следом `_loadPractice`. Порядок
завершения чтений не гарантирован — счётчик может «прыгнуть назад».

**Почему это важнее, чем выглядит**: БФТ описывает целевой сценарий буквально
как быстрый многократный тап — счёт мантр на ходу, крупная кнопка, П1 с нёндро
на 100 000. Это не редкий edge case, это основной режим работы приложения.

**Заодно**: `incrementCount` сделан как read-modify-write внутри транзакции
(`practice_repository.dart:46-71`). Один `UPDATE ... SET current_count =
current_count + ?` убирает и лишнее чтение, и весь класс гонок на уровне БД.

**Дизайн**: кнопки `+1/+10/+100` — обычные `ElevatedButton` в `Row`.
SCR-9 требует «крупную кнопку +», UX-цель — крупные тач-цели для счёта на ходу.

## B-9 — форма создания: четыре бага в одном методе

`create_practice_screen.dart:31-52`:

- **Двойное создание** — кнопка «Создать» не блокируется на время
  `await repository.create(...)`; два тапа дают две практики.
- **Имя из пробелов** — валидатор проверяет `value?.isEmpty` (строка 69),
  а не `trim().isEmpty`.
- **Цель теряется молча** — `int.tryParse` (строка 39) вернёт `null` для
  «100 000» с пробелом или «abc»: пользователь ввёл цель, нажал «Создать»,
  цели нет и никто не сказал почему. Отрицательные значения проходят.
- **Единица измерения** пишется через `onChanged` без контроллера и без `trim` —
  пустая строка вместо `null`.

**Про тесты**: три теста экрана проверяют только валидацию пустого имени и то,
что в поля можно печатать. Путь сохранения не покрыт ни одним тестом —
поэтому все четыре бага и живы.

## B-10 — `create()` молча выбрасывает `createdAt` и `updatedAt`

`PracticeEntity` требует оба поля как `required`. Сгенерированный
`PracticesCompanion.insert` их принимает (`app_database.g.dart:725-738`).
А репозиторий их не передаёт:

```dart
// practice_repository.dart:32-42
PracticesCompanion.insert(
  presetId: Value(practice.presetId),
  name: practice.name,
  type: practice.type,
  target: Value(practice.target),
  unit: Value(practice.unit),
  traditionTag: practice.traditionTag,
  currentCount: Value(practice.currentCount),
  // createdAt / updatedAt не переданы -> молча берутся дефолты БД
)
```

Весь вызывающий код — `DevSeeder`, форма создания, все девять тестов —
добросовестно вычисляет `final now = DateTime.now()`, и это значение
выбрасывается. Обязательные параметры модели оказываются ложью для пути записи.

**Когда взорвётся**: при массовой вставке практик из пресета (B-3) все строки
получат один timestamp с точностью до секунды, а список сортируется
`orderBy(createdAt)` — порядок трекеров станет недетерминированным.
Дальше — импорт бэкапа из бэклога v1.1, где чужие даты обязаны сохраняться.

## B-11 — история счёта осиротеет, внешний ключ не работает

`CountHistory.practiceId` объявлен как `.references(Practices, #id)`
(`tracker_tables.dart:20`), но Drift **не включает `PRAGMA foreign_keys`
по умолчанию**, и каскада тут нет. Ограничение существует только на бумаге.

- `delete()` (`practice_repository.dart:74-78`) удаляет практику, оставляя
  её историю в БД навсегда. Строки не видны, не чистятся и растут.
- Если внешние ключи когда-нибудь включат — то же удаление начнёт падать.
- `_cleanupOldPreset` — пустая заглушка (`preset_manager.dart:91-94`), так что
  `switchPreset` и `resetPreset` не чистят ничего. Обещание FR-ONB-4
  не выполняется с обеих сторон: и данные не изолируются, и мусор не убирается.

# Архитектура, тесты, процесс

## R-9 — ядро импортирует фичу (нарушен принцип №1 конституции)

```dart
// lib/core/db/app_database.dart:8
import '../../features/tracker/data/tracker_tables.dart';

// lib/core/db/dev_seeder.dart:1-2
import '../../features/tracker/data/practice_repository.dart';
import '../../features/tracker/domain/practice.dart';
```

AGENT.md: «Ядро не знает о конкретных школах/модулях». Сейчас ядро
не собирается без `features/tracker`. С появлением календаря и контента
аннотация `@DriftDatabase(tables: [...])` превратится в реестр всех фич
внутри ядра — ровно в ту связность, которой D-5 должен был не допустить.

**Развилка** (нужно решение оркестратора): либо ядро объявляет только
собственные таблицы, а фичи регистрируют свои через `DriftDatabase.modular` /
отдельные `DatabaseAccessor`; либо решение «одна БД со всеми таблицами в ядре»
фиксируется явным `D-` с честной формулировкой «принцип №1 ослаблен для слоя БД,
потому что…». Молчаливое нарушение хуже любого из двух вариантов.

## R-10 — guard-тест изоляции дырявый

```dart

final importRegex = RegExp(
```

**Почему это угроза**: этот тест — единственный механизм, защищающий D-5,

## R-11 — service locator вместо Riverpod (нарушение D-4)

```dart
// practice_provider.dart:15-21
final practiceRepositoryProvider = Provider<PracticeRepository>((ref) {
  final module = ModuleRegistry.instance.get('database');   // глобаль + строковый ключ
  if (module is! DatabaseModule) {
    throw StateError('DatabaseModule not registered');      // + приведение типа в рантайме
  }
  return PracticeRepository(module.database);
});
```

D-4 объявляет Riverpod единственным DI. Здесь Riverpod — обёртка вокруг
глобального реестра со строковыми ключами: тот же паттерн, что у `get_it`,
только без его гарантий. AGENT.md отдельным пунктом запрещает «глобальные
переменные для состояния» — а `ModuleRegistry.instance`, `EventBus.instance`
и верхнеуровневый `trackerRouter` именно ими и являются.

**Цена уже платится**: тесты вынуждены делать `ModuleRegistry.instance.disposeAll()`
в `setUp` (`app_module_test.dart:64-67`, `registry_integration_test.dart:12-15`).
Это межтестовая связность — перестановка или параллельный прогон уже небезопасны.

## R-12 — `EventBus` умирает навсегда, и тест его убивает

`dispose()` (`event_bus.dart:28-30`) закрывает `StreamController` синглтона,
пересоздать нечем. После этого `publish` молча глотает события — проверка
`if (!_controller.isClosed)` превращает ошибку в тишину.

```dart
// event_bus_test.dart:83-100
test('dispose closes the stream', () async {
  final bus = EventBus.instance;
  bus.dispose();            // закрывает ГЛОБАЛЬНУЮ шину на весь файл
  ...
});
```

Тест проходит только потому, что объявлен последним в файле. Любой новый тест,
дописанный ниже, будет молча получать пустоту — и разбираться придётся долго,
потому что падение выглядит как «событие просто не пришло».

**Отдельно**: в `main.dart` шина не диспозится и не используется вообще.
D-7 реализован и ни к чему не подключён.

## R-13 — `DatabaseModule` неинъектируем, тесты в шаге от записи в реальную ФС

`init()` (`database_module.dart:30-33`) жёстко создаёт `AppDatabase()`, который
открывает файл в `getApplicationDocumentsDirectory()`. Конструктора
с `QueryExecutor` нет, хотя у `AppDatabase` он есть (`forTesting`).

`registry_integration_test.dart` и `database_module_test.dart` создают
**настоящий** `DatabaseModule`. Спасает только лень `LazyDatabase`: соединение
не открывается, пока не выполнен первый запрос. Первый же тест, который сделает
запрос, начнёт писать в документы разработчика и в CI-раннер.

**Фикс**: `DatabaseModule({QueryExecutor? executor})`.

## R-14 — два источника истины в таблице `presets`

Колонки `name`, `version`, `tradition` (`app_database.dart:29-40`) дублируют поля
внутри JSON в колонке `data`. При чтении (`preset_manager.dart:87-88`)
используется только `data`, колонки — только при записи. Они могут разойтись,
и никто не заметит: ни тест, ни рантайм.

## R-15 — локализации нет, а приложение только на русском

В `pubspec.yaml` нет `flutter_localizations` и `intl`; у `MaterialApp.router`
не заданы `localizationsDelegates` и `supportedLocales` (`main.dart:47-50`).
Папка `lib/shared/l10n/` содержит только `.gitkeep`.

**Следствие**: все системные строки Material — кнопки диалогов, выбор даты

**Почему сейчас, а не в Этапе 8**: Этап 6 — это выбор времени доставки

# Четыре урока

Не про эти конкретные баги, а про то, как они появились — и почему следующая
дюжина появится так же, если ничего не менять в процессе.

## Урок 1. Зелёный тест — это не гарантия, это утверждение о гарантии

Guard-тест изоляции зелёный, и на него ссылаются три документа. При этом он
не ловит относительные импорты, не проверяет направление core → features,
а половина файла — `expect(true, isTrue)`. Ровно в той зоне, которую он
«охраняет», сейчас лежит нарушение R-9.

Проверка простая, и её стоит делать при приёмке каждого guard-теста:
**внести нарушение руками и убедиться, что тест покраснел.** Тест, который
никогда не падал, не доказал ничего.

## Урок 2. Критерий выхода этапа — это демонстрируемый сценарий, а не набор файлов

«Применение пресета создаёт записи в БД» было отмечено ✅ при том, что
`applyPreset` создаёт одну строку в `presets` и ни одной практики. Формально
файл есть, класс есть, тесты зелёные. Сценария нет: пройти его невозможно,
потому что вызвать `applyPreset` из приложения нельзя.

Критерий должен формулироваться так, чтобы его можно было предъявить:
*«на чистой установке выбираю Ньингма → в списке появляются четыре практики
нёндро → тапаю → счёт растёт → после перезапуска сохранился»*. Такой критерий
нельзя закрыть, не сделав работу.

## Урок 3. Чините на том слое, где живёт причина

По B-2 STATE.md предлагает «ограничить прогресс в UI». Причина живёт в доменной
модели, и UI-фикс придётся повторить в дашборде, в истории, в виджете
домашнего экрана — три будущих шанса забыть.

Тот же вопрос по B-1 задан правильно: D-16 выбирает `.watch()` вместо точечного
`invalidate` именно потому, что «решает системно». Хороший инстинкт — осталось
применить его последовательно.

## Урок 4. Не заводите тесты, которые проверяют, что виджет отрисовался

Девять тестов трекера покрывают: «экран показывает список», «есть FAB»,
«можно ввести текст в поле», «валидатор ругается на пустое имя». Ни один
не проходит путь *сохранения*. Поэтому четыре бага формы (B-9) живут в коде,
формально покрытом тестами.

Тест должен ломаться от неправильного поведения, а не от удаления виджета.
«Тапнул Создать дважды → в БД одна запись», «ввёл 150 при цели 100 → прогресс
100%, счёт 150» — вот такие тесты стоило написать вместо трёх проверок,
что `TextFormField` принимает текст.

# Мелочи заодно

- **Пустой список — пустой экран.** `ListView.builder` с нулём элементов
  не рисует ничего; SCR-8 требует объяснение и кнопку «Создать». Это первое,
  что увидит новый пользователь после онбординга.
- **Висячий пробел** в `'${currentCount} ${unit ?? ''}'`
  (`practice_list_screen.dart:28`).
- **Смешение Navigator 1 и go_router**: `Navigator.of(context).pop(true)`
  при навигации через `context.push` (`create_practice_screen.dart:49`).
- **`disposeAll` без `try/finally`** — исключение в одном модуле оставит реестр
  наполовину разобранным (`module_registry.dart:45-51`).
- **`PresetSchema.fromJson` без валидации** — падает `TypeError` на любом кривом
  поле, и тест закрепляет это как ожидаемое поведение. Для пользовательских
  пресетов (FR-PRS-3) нужна внятная ошибка.
- **Нет `copyWith`** у `PracticeEntity` — десять полей и никакого способа
  изменить одно.
- **Порядок инициализации модулей неявный.** `PresetManager.init()` работает
  только потому, что `DatabaseModule` и `StorageModule` зарегистрированы раньше.
  Зависимости нигде не объявлены — перестановка двух строк в `main.dart` ломает старт.
- **README и `description`** — дефолтный шаблон Flutter («A new Flutter project»).

# Что хорошо

Список выше длинный, поэтому важно сказать и обратное: для четырёх этапов это
очень приличная база, и большая часть находок — следствие того, что каркас
построен раньше, чем к нему подключили UI.

- `AppModule` с явным жизненным циклом и предсказуемым порядком `dispose` —
  честный, маленький контракт.
- Слой данных отделён от Drift-моделей (D-13), `PracticeEntity` не течёт наружу.
  Переход на `.watch()` из-за этого будет дешёвым.
- Тест персистентности с настоящим файлом БД и двумя сессиями
  (`practice_repository_test.dart:11-51`) — именно так и надо проверять,
  что данные переживают перезапуск.
- `strict-casts`, `strict-inference`, `strict-raw-types` включены с самого
  начала. Это редко и правильно.
- Лениво открываемая БД через колбэк в `PresetManager` (R-6) — аккуратное
  решение реальной проблемы, а не обход.
- Сама дисциплина STATE.md с `H-/F-/D-/R-` работает: именно благодаря ей
  этот отчёт удалось написать за один проход и привязать к существующей
  нумерации. Проблема не в системе, а в том, что записи перестали
  сверяться с кодом.
