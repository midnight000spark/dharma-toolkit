<a id="d-17"></a>
### D-17: миграции пишем вручную, `stepByStep` откладываем до доступного тулчейна
- **Описание**: `onUpgrade` применяет версии по одной через приватный `_migrateToVersion(Migrator, int)`; каждая версия обязана иметь свою ветку, неизвестная версия бросает `StateError`. Новые таблицы — `createTable`, новые колонки — `addColumn`; `createAll()` в ветках запрещён.
- **Причина**: `stepByStep` требует сгенерированных файлов (`drift_schemas/*.json`, файл шагов). На момент реализации 5.0.1 Dart/Flutter в среде отсутствовали, сгенерировать их было нечем, а ссылаться из `lib/` на несуществующий сгенерированный файл нельзя — проект перестал бы собираться.
- **Альтернативы**: (а) `stepByStep` — цель остаётся, переход выполняется заменой тела `onUpgrade` и ничего не ломает; (б) оставить `createAll()` — отвергнуто, это и есть R-8.
- **Дата**: 2026-08-31
- **Отклонение от плана**: ревью 5.0 предлагало сразу `stepByStep`. Существо R-7/R-8 закрыто, форма отличается. Процедура перехода — `docs/MIGRATIONS.md`.

<a id="d-18"></a>
### D-18: точная арифметика тибетского календаря — Rational на BigInt
- **Описание**: астрономические вычисления порта tibcal (долгота луны/солнца, титхи, накшатры) ведутся на точных рациональных числах (`Rational` поверх `BigInt`), а не на `double`.
- **Причина**: исходный tibcal использует точную рациональную арифметику Python (`fractions.Fraction`); `double` даёт накопленную ошибку у границ дней — а в тибетском календаре цена ошибки — сдвиг пропущенного/двойного дня (F-2).
- **Альтернативы**: `double` (отвергнуто — точность у границ), decimal-пакеты (избыточны, не выражают дроби отBigInt-точного вида).
- **Дата**: 2026-09-01

### D-20: точка агрегации схемы БД в core/db — единственное ослабление принципа №1
- **Описание**: ядро (`lib/core/db/app_database.dart`) объявляет `@DriftDatabase(tables: [...])` со таблицами всех фич. Остальное ядро импортировать features не вправе; guard-тест проверяет core→features (кроме `core/db`) и feature→feature.

- **Альтернативы**: `DriftDatabase.modular` / отдельные `DatabaseAccessor` по фичам — дороже, ломает единый трек миграций.

<a id="d-32"></a>
### D-32: выбор реализации календаря — только по тегу активного пресета; `moduleConfigs` удалён из схемы пресета
- **Описание**: второго источника истины о выборе календаря не существует: поля
  `moduleConfigs` (`tracker.isolationTag`, `calendar.type/school/highlightDays/uposatha`)
  убраны из `PresetSchema` и из shipping-пресетов, легаси-JSON со строками в таблице
  `presets` продолжает читаться (неизвестные ключи игнорируются), `toJson` их не
  возвращает. Связь «тег → реализация» живёт в одном месте — реестре
  `calendarProviderForTagProvider` (фича календаря), неизвестный тег даёт честный
  `null` («календаря для этой традиции нет»), а не чужой календарь.
- **Причина**: закрывает R-20 (мёртвая конфигурация = второй источник истины, родственник
  B-4/R-14); вариант «оставить поле и сделать его контрактом» означал бы живую ветвящуюся
  конфигурацию, читаемую из JSON, то есть путь, по которому правка пресета молча меняет
  реализацию. Реестр в коде — типизирован и охраняется тестами.
- **Альтернативы**: (а) принят; (б) `moduleConfigs.calendar.type` как контракт выбора —
  отвергнуто (тот же второй источник, только «узаконенный»); (в) помечать reserved-полем —

### D-36: стратегия планирования уведомлений
- **Описание**: горизонт — 60 дней вперёд (pending ≤ 64 — под iOS-лимит F-57,
  ассерт в тесте); триггеры перепланирования — **старт приложения / смена
  пресета / смена настроек**; перепланирование идемпотентно: cancelAll своего
  диапазона id (100000–199999) + schedule заново; дефолт настроек — вкл /
  08:00 local; доставка — exact при доступном SCHEDULE_EXACT_ALARM, иначе
  честный inexact (без вранья о точности); канал — тихий (importance low,
  без срочности — UX-A-2: не будильник, а напоминание). Риск vendor-политик
  против exact — заводится как угроза в пакете 6.3 (по итогу реализации).
- **Причина**: дневные особые дни не требуют точности до секунды, но требуют
  предсказуемости объёма pending; cancel-by-диапазону не трогает чужие id;
  60 дней ≈ 2–4 особых дня/неделю с запасом под паки.
- **Альтернативы**: вечный повторяющийся daily-триггер с самопроверкой (отвергнуто —
  лишняя нагрузка и ложные срабатывания); горизонт «весь год» (отвергнуто — iOS
  64 pending, дубли); точный alarmClock (отвергнуто — USE_EXACT_ALARM под аудит
  стора, приложение не будильник).
- **Дата**: 2026-09-02
