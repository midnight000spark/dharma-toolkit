## 3. Артефакт 1 — `CALENDAR_MODEL.md`

### 3.1 Что это

Спецификация «Математическая модель календаря» (draft v1.0, 2026-09-24),
описывает расчёт для **четырёх** традиций: Пхугпа, Цурпху (Цурлуг), Шен Бон
(Юнгдрунг Бон) и Тхеравада. Структура: архитектура слоёв → движок A (Калачакра)
→ движок B (ЮВА/Тхеравада) → слой праздников → сквозные критерии → тест-векторы.

### 3.2 Ключевые тезисы документа

- **Две независимые системы (E1):** движок A (тибетская Калачакра) и движок B
  (ЮВА/Тхеравада) не конвертируются друг в друга напрямую — только через
  гражданскую дату.
- **Движок A параметризуется (E2):** традиция = набор параметров + свой словарь
  праздников. Эпохи и коэффициенты выписаны для Пхугпа (1687/1681/1927,
  generalized epoch −1000) и Цурпху (1732/1824/1852/1987 Sherab Ling).
- **Различие Пхугпа/Цурпху сведено к параметрам:** Солнце по сиддханте против
  карана (`byed rtsis`), а високосный месяц — по сиддханта-индексу и там, и там;
  на структуру дней/интеркаляцию это «не влияет» (но см. §5.3 — на 2027 влияет
  на номер месяца).
- **Бон (B6) честно помечен как нерешённый:** открытого алгоритма нет,
  предлагается **процедура калибровки** — собрать 30+ лет официальных календарей
  Menri/Triten Norbutse (1960–2030) и подобрать epoch+константы к движку A;
  если не сходится — табличный слой без полного вывода. Лосар Бона может
  отличаться от Пхугпа до ±1 месяца.
- **Тхеравада (движок B):** Тай (Suriyayatra, метонов цикл 7/19), Мьянма
  (Thandeikta, табличный цикл), Шри-Ланка (Poya по правительственной газете +
  локальная таблица «год → даты»), солнечные события (Сонгкран = тропическая
  долгота Солнца 0°, VSOP87-lite).
- **Сквозные требования (W1–W7):** детерминизм на BigInt, golden-тесты
  (2000–2030, желательно 1900–2100), граничные кейсы (вставной месяц, пропуск
  30-го титхи, `zla bshol`), производительность (<10 мс месяц, офлайн-кэш),
  локализация ru/en/тибетский, таймзона и якорный меридиан как параметр, подсветка
  только по факту.
- **Слой праздников (P-1…P-4):** правило наблюдения на пропущенном/удвоенном
  дне, оверлей нескольких традиций на одну дату, приоритеты, словарь
  `lunar_date + observance_rule + per_school_flag` с source-ссылкой.
- **Тест-векторы (§8)** — 6 событий на 2026/2027 с конкретными григорианскими
  датами (см. §5.1 — они сверены с xlsx).

### 3.3 Полезность для проекта

- **Прямое попадание в бэклог v1.1 (D-30 / F-67):** план «параметризация
  Phugpa-движка + отдельный пак событий» документ раскладывает на конкретные
  коэффициенты/эпохи/критерии. Это чертёж research-библиотеки Бона.
- **Закрывает вопрос «а что дальше после Пхугпа»:** Цурпху как профиль того же
  движка A — дешёвый способ покрыть Кагью без новой математики.
- **Движок B** описывает то, чего в проекте нет вообще: у нас упосатха — по
  фазе Луны (Meeus), а не лунно-солнечный календарь Тхеры/Тая/Мьянмы.
- **Критерии приёмки (K1–K5, T1–T3, B1–B4, V1–V3, W1–W7)** — готовая заготовка
  под golden-тесты; часть из них мы можем проверить уже сегодня нашим портом.
- **Оговорка по качеству:** документ — draft, с опечатками и оборванными
  фразами («начинаетcj», «важим», «помоздний»), и он **не является
  первоисточником** — он компилирует TCG/мен-це-кханг/румтек, но ссылок на
  каждый коэффициент не даёт. Tier-0-правило требует первоисточник.

1. **Это ровно тот «пак прочих праздников», которого нет.** Провайдер

2. **MVP-срез закрывает Ньингма почти целиком** (4 строки Ньингма + ядро Пхугпа),
   а `Пхугпа`-строки обслуживают Ньингму и без изменений.
3. **Регулярные дни** (8/10/15/25/29/30 каждого лунного месяца) — это готовый

4. **Даты Цурпху-2027, включая «вычисляемые из сочетаний элементов»**

5. **Два года (2026–2027)** дают проверяемое окно, пересекающееся с нашим

### 5.2 Итог сверки с портом

```
ИТОГ: ok = 57, bad = 10 (всего 67 векторов)
```

- **57 совпадений** — лунная дата и григорианская дата согласованы с нашим
  портом Пхугпа. Для MVP-среза это в основном чистая зона.
- **8 из 10 расхождений — Цурпху-2027** (`Цурпху Карма Кагью`, колонка 2027):
  порт (Пхугпа) даёт **номер месяца на 1 меньше**, чем таблица: например
  `Сага Дава Дючен` таблица `4/15 → 20.05.2027`, порт `3/15 → 20.05.2027`;
  `Чокхор` `6/4`, порт `5/4`; `Лхабаб` `9/22`, порт `8/22` и т. д.
  Это **ожидаемое и уже описанное** расхождение: в 2027 (tib 2154) вставные
  месяцы у Пхугпа и Цурпху стоят в разных местах года, поэтому нумерация
  месяцев сдвигается. Документ прямо это фиксирует (T2/T3: «2027 различаются»,
  «порт Пхугпа невалиден для Цурпху-2027»). **Не ошибка таблицы, а подтверждение
  того, что её колонка Цурпху — не копия Пхугпа.**
- **2 из 10 — реальные флаги** (Q2 Сакья Пандита, Q3 Ломба) — разобраны в §4.4,
  лог в `validation-disputed.md`.

### 5.3 Побочное наблюдение (расхождение документа с кодом)

Документ (T3) говорит о «дублированном **1-м** месяце у Пхугпа 2154», а наш порт
даёт вставной **2-й** месяц (`2/1` вставной = 09.03.2027), а `8/1` в 2027 вовсе
не существует. Это либо разница конвенций нумерации, либо неточность draft'а.
Формулировка «doubled 1st month» может означать «первый по счёту дублированный
месяц года» — тогда противоречия нет. **Требует сверки с первоисточником TCG**,
утверждать не берусь. Отдельно: `m8 normal=ERR` — 8/1 в tib-2027 у порта
отсутствует (пропуск) — это ровно класс FR-CAL-6, но стоит перепроверить.

### 5.4 Проверка дат Тхеравады по фазе Луны

Для 12 дат (6 событий × 2 года) вычислили фазу Луны нашим Meeus-модулем
(0.5 = полнолуние). Результат (`validation-moon.md`):

- 7 из 12 — близко к полнолунию (в пределах ~1,5 суток);
- 3 из 12 — «на следующий день после полнолуния» (Васса — так и задумано);
- **1 из 12 — не полнолуние:** `День Анапанасати 05.11.2026`, фаза 0.876 (Q4);
- 1 из 12 — на границе (`Магха Пуджа 21.02.2027, phase 0.5205`).

Важно: для Тхеравады мы проверили только астрономическую правдоподобность
(полнолуние), **не** правильность номеров лунных месяцев Тая/Мьянмы — у нас
нет движка B, и таблица не указывает регион (Таиланд? Мьянма? Шри-Ланка?),
хотя даты различаются между ними. Это открытый вопрос к автору таблицы.

## 7. Чего не хватает для интеграции (гэпы)

### 7.1 Гэп схемы пака событий (D-35, v1)

Сегодня `EventDateRuleKind` знает только **два** вида правил:
`tibetan {month, day}` и `gregorianYearly {month, day}`. Таблица требует
существенно большего:

| Что в таблице | Поддержано? |
|---|---|
| одиночная тибетская дата (месяц+день) | ✅ |
| фиксированная григорианская дата (дни рождения Кармап) | ✅ |
| **регулярный день «каждого лунного месяца»** (день без месяца) | ❌ нужен `tibetanMonthly {day}` |
| **диапазон дней** (Монлам 2–15, Сага Дава 1–30, Ташилунпо 14–16) | ❌ нужен диапазон / `endDay` |
| **лунно-солнечный календарь Тхеры** (месяцы иной системы) | ❌ нужен движок B |
| **система «Хорды» для Бона** | ❌ нужен профиль движка A |
| **дни из «сочетаний элементов»** (Паден/Лютеп/Ньинак/Йеконг) | ❌ алгоритма нет; пока только таблица дат |
| «по объявлению» | ❌ не дата |

Вывод: **таблица — это драйвер для схемы паков v2**, а не то, что влезает в v1
без потерь. Если интегрировать только MVP-срез, можно обойтись расширением
`tibetanMonthly` + диапазоном — это честный минимум.

### 7.2 Гэп домена

- `SpecialDayType` не различает «неблагоприятный день», «перенесённый день»,
  «день защитника» — сейчас всё это схлопнется в `festival`. Для MVP это нормально
  (расширяемость в enum заложена), но для Кагьюv1.1 понадобится.
- У `SpecialDay` нет поля «правило наблюдения на пропущенном/удвоенном дне»
  (P-1 документа) — есть только факт `isLeapDay` на уровне порта.
- Нет источника (`source`) на уровне `SpecialDay` — а для паков он обязателен.

### 7.3 Гэп движков

- У нас **нет движка B** (Тхеравада-праздники); есть только упосатха по фазе Луны.
- У нас **нет профиля Цурпху** (порт Пхугпа для Цурпху-2027 невалиден — §5.2).
- У нас **нет бонского профиля/калибровки** (D-30 — это research-задача).
- `CALENDAR_MODEL.md` предлагает путь `lib/features/calendar/engine/` — в текущей
  структуре движок лежит в `lib/features/calendar/data/tibetan/`; перед
  интеграцией спецификации нужно согласовать структуру, а не копировать путь.
