# Дхарма-тулкит — Архитектурная конституция

**Версия 2.2** · 2026-09-01 · пересмотрена по итогам внешнего аудита (`docs/REVIEW-2026-08-31.md`)

## Миссия
Создать универсальное мобильное приложение для буддийских практикующих, объединяющее календарь, счетчики практик и контент под разные традиции.

## Иерархия документов (приоритет источников)

**БФТ → ROADMAP → STATE → AGENT → код-комментарии**

- **БФТ** (`docs/BFT-v1.1.md`) — что строим и для кого. Источник требований.
- **ROADMAP.md** — куда идём, порядок этапов. Меняется только с одобрения оркестратора.
- **STATE.md** — где мы сейчас: статусы, факты, решения, угрозы, баги.
- **AGENT.md** (этот файл) — как работаем: принципы и правила приёмки.
- **Комментарии в коде** — lowest priority, не источник истины о проекте.

**Правило согласования (урок 4 аудита, R-17):** при любом конфликте
между документом и кодом **главный источник правды о факте — код**.
Документ, расходящийся с кодом, — это баг документа: сначала правим
документ, потом работаем. Отметка «сделано» в документе обязана
подтверждаться командой проверки (см. «Правила приёмки»).

## Архитектурные принципы

### 1. Модульность (Plugin Architecture)
- Ядро не знает о конкретных школах/традициях
- Каждый модуль — независимый плагин с четким интерфейсом
- Модули общаются только через event bus или dependency injection
- Запрещены прямые импорты между модулями
- **Единственное ослабление (D-20):** точка агрегации схемы БД —
  `lib/core/db/app_database.dart`. Ядро объявляет `@DriftDatabase(tables: [...])`
  со таблицами всех фич, потому что Drift при AOT не поддерживает динамическую
  регистрацию таблиц, а единый миграционный трек важнее изоляции слоя данных.
  Ослабление **зафиксировано и не расширяется**: остальное ядро (events, config,
  module) импортировать features не вправе; guard-тест проверяет оба направления
  (core→features, кроме `core/db`, и feature→feature).

### 2. Конфигурируемость через пресеты
- Школы/традиции = JSON-файлы (пресеты), не хардкод
- Пресет описывает какие модули включить и с какими настройками
- Пользователь может создавать свои пресеты
- Применение пресета **обязано материализовывать данные** (создавать трекеры
  из `preset.practices` идемпотентно) — пресет, который «загружен, но ничего
  не создаёт», не считается работающим (B-3).

### 3. Изоляция данных
- У каждой традиции свои данные в БД (с префиксами/тэгами)
- Общие модули (календарь, счетчик) работают с данными абстрактно
- Возможность иметь несколько активных традиций одновременно
- `traditionTag` берётся из активного пресета, а не из литерала в коде (B-4)

### 4. Dependency Injection (D-4 + D-22)
- **Riverpod — единственная система DI.** Service locator (`ModuleRegistry.instance.get('...')`
  со строковым ключом и приведением типа в рантайме) запрещён — это паттерн
  get_it, от которого отказались.
- Зависимости в UI-слой и репозитории приходят через провайдеры
  (например, провайдер `AppDatabase` с оверрайдом в `ProviderScope`).
- Глобальные переменные для состояния запрещены.
- Модули, которым нужна БД, получают её через инъекцию (`QueryExecutor` /
  экземпляр), а не создают сами (R-13).

### 5. Миграции БД (D-17)
- `onUpgrade` применяет версии **по одной**; каждая версия схемы обязана иметь
  свою ветку; неизвестная версия бросает `StateError` при открытии базы
  (падает у разработчика, а не молчит у пользователя).
- Новые таблицы — `m.createTable`, новые колонки — `m.addColumn`;
  `createAll()` в ветках миграций **запрещён**.
- `stepByStep` с дампами схемы — целевая форма; переход на неё выполняется
  заменой тела `onUpgrade` и не ломает существующие ветки (процедура: `docs/MIGRATIONS.md`).
- Каждое изменение схемы сопровождается тестом миграции, проверяющим
  **сохранность данных** при переходе версий.

### 6. EventBus (D-7, отложен по D-21)
- Event bus — низкоуровневый транспорт, не состояние UI.
- **D-21: шина отложена до реального потребителя (Этап 6).** В Этапе 5
  междомодульные коммуникации идут через Riverpod-провайдеры и Drift-стримы.
- До подключения шина обязана быть инстанцируемой (тестируемой локально,
  без необратимого `dispose` глобального синглтона) — R-12.

## Технологический стек (подтвержден)
- **Framework**: Flutter 3.47.1 (stable), Dart 3.13.1
- **State Management**: Riverpod (flutter_riverpod 2.6.1) — state + DI (D-4)
- **Local DB**: Drift (фактически 2.34.3, F-24 — документацию сверять с pubspec.lock)
- **Routing**: go_router 18.0.0
- **Testing**: flutter_test (mocktail — добавить при появлении потребности)
- **Локализация**: flutter_localizations + intl, только `ru` (план 5.0.5, R-15)

## Работа с ROADMAP.md

### Обязательный порядок чтения
1. **Перед каждым этапом** — перечитай ROADMAP.md для понимания контекста и цели этапа
2. **Перед каждым шагом** — перечитай STATE.md для понимания текущего статуса
3. **AGENT.md** — перечитывай только в начале этапа или при потере архитектурного контекста

### Правила изменения ROADMAP.md
- ROADMAP.md изменяется ТОЛЬКО с одобрения оркестратора (человека)
- Любое изменение фиксируется в секции "Changelog плана" с датой
- dharma не имеет права менять ROADMAP.md без явной инструкции

## Tier-0: Документация библиотек
Перед работой с любой внешней библиотекой/пакетом:
1. Прочитай официальную документацию (pub.dev / README / API docs)
2. Сверь API с текущей версией Flutter/Dart (deprecated — как в F-16)
3. Зафиксируй ключевые факты в STATE.md (версия, API, ограничения, лицензия)
4. Только после этого пиши код
5. Версии сверяй с `pubspec.lock`, а не с ограничениями `pubspec.yaml` (F-24)

## Правила приёмки (уроки аудита 2026-08-31)

### Урок 1. Зелёный тест — это утверждение о гарантии, а не гарантия
Guard-тест принимается только так: **внести нарушение руками и убедиться,
что тест покраснел.** Тест, который не мог упасть, не доказал ничего.
Заглушки `expect(true, isTrue)` запрещены.

### Урок 2. Критерий выхода этапа — демонстрируемый сценарий
Формулировка вида «применение пресета создаёт записи в БД» закрывается только
предъявляемым прогоном: *«на чистой установке выбираю Ньингма → появляются
практики нёндро → тапаю → счёт растёт → после перезапуска сохранился».*
Набор файлов/классов/зелёных юнит-тестов критерием не является.

### Урок 3. Чинить на слое причины
Диагноз бага обязан указывать слой, где живёт причина (домен, а не UI для B-2;
слой данных для B-1). Точечные UI-костыли, которые надо повторять в каждом
новом месте, запрещены.

### Урок 4. Тесты должны ломаться от неправильного поведения
Тест проверяет поведение (путь сохранения, гонку, границy), а не факт отрисовки
виджета. «Форма покрыта тестами» без покрытия пути сохранения — не покрыта.

### Общее правило
Каждое «сделано/✅/☑️» в любом документе подтверждается командой проверки
или предъявляемым сценарием. Не подтверждено — статус снимается.

## Модельная стратегия (D-19)
- **Qwen3.7 Plus выведен из эксплуатации** (недельный лимит исчерпан,
  стоимость росла нелинейно с контекстом — F-30).
- Разработка — только новые сессии на **Qwen3.8 Flash (variant high)**.
- Тяжёлые операции (синхронизация docs, большие пакеты) — только в свежем
  контексте.
- Глубина размышления: high — базово; max — для спайка 5a, проектирования
  новых абстракций и диагностики повторяющихся отказов; после max-подпакетов
  обновлять сессию (preserve_thinking раздувает контекст).

## Нотификации (D-27)
Агент отправляет уведомления через скилл `telegram-notify` в трёх точках:
- Завершение пакета: `✅ <пакет>: <итог>, тесты N/N`
- Стоп-гейт: `🛑 СТОП <пакет>: <причина>`
- Ручная приёмка: `👀 <пакет>: зелёный, прогони сценарий: <сценарий>`
Вызов: `./scripts/notify.sh "<сообщение>"`.
Сообщения ≤200 символов, без кода и путей. Fail-silent: при отсутствии
конфига скрипт молча exit 0, пакет не падает. Токен вне репо
(`~/.config/dharma/telegram`, 600) — коммитить запрещено.

## Правила кода

### Запрещено
- Хардкодить названия школ в ядре и в навигации (traditionTag из пресета)
- Создавать циклические зависимости между модулями
- Писать код без тестов
- Использовать глобальные переменные для состояния
- Service locator вместо провайдеров (D-4/D-22)
- `createAll()` в ветках миграций (D-17)
- Заглушки тестов `expect(true, isTrue)` (урок 1)

### Обязательно
- Каждому модулю — свой набор тестов
- Интерфейсы для всех внешних зависимостей
- Документация к публичным API
- Коммиты по Conventional Commits
- Обновление STATE.md каждый шаг; снятие статусов «сделано» при расхождении с кодом

### Коммиты
- `feat(module_name):` — новый функционал
- `fix(module_name):` — исправление бага
- `refactor(module_name):` — рефакторинг
- `test(module_name):` — добавление тестов
- `docs:` — документация
- `chore:` — инфраструктура

## Схема классификации информации (для STATE.md)

### [ГИПОТЕЗА] — H-{номер}
Предположения, требующие проверки.
```
- **H-{номер}**: {Описание}
  - Статус: [новая|тестируется|подтверждена|опровергнута]
  - Как проверить: {план проверки}
  - Результат: {заполняется после проверки}
```

### [ФАКТ] — F-{номер}
Подтвержденная информация.
```
- **F-{номер}**: {Описание}
  - Источник: {откуда известно}
  - Дата: {когда подтверждено}
```

### [РЕШЕНИЕ] — D-{номер}
Принятые архитектурные решения.
```
- **D-{номер}**: {Описание}
  - Причина: {почему это}
  - Альтернативы: {что еще рассматривали}
  - Дата: {когда принято}
```

### [УГРОЗА] — R-{номер}
Риски и проблемы.
```
- **R-{номер}**: {Описание}
  - Вероятность: [низкая|средняя|высокая]
  - Влияние: [низкое|среднее|критическое]
  - Митигация: {как бороться}
  - Статус: [открыта|в работе|закрыта]
```

## Вход в курс (свежая сессия)

Постоянное правило для каждой новой сессии агента. Порядок восстановления
контекста до первого действия:

1. **CONTEXT.md** — суть и статус проекта за 30 секунд.
2. **STATE.md** — факты, решения, баги, «Следующее действие».
3. **ROADMAP.md** — критерии текущего этапа.
4. **AGENT.md** — конституция и правила приёмки.
5. **Базовая линия** до первой правки: `flutter analyze` (0 проблем),
   `flutter test` (все зелёные), `git status` (чисто), `git tag -l`
   (ожидаемые теги на месте). Любое расхождение — СТОП и отчёт.
6. **Документ противоречит коду — код истина.** Расхождение фиксировать
   в STATE.md как [ФАКТ] или [УГРОЗА] R-17.
