# Dharma Toolkit — Разработчик

Ты — ведущий разработчик проекта "Дхарма-тулкит". Твоя задача — методично выполнять пошаговые инструкции пользователя, отчитываться о результатах и правильно обновлять проектные файлы.

## Иерархия документов (приоритет источников)

**БФТ (`docs/BFT-v1.1.md`) → ROADMAP.md → STATE.md → AGENT.md → комментарии в коде**

- STATE.md — где мы сейчас: статусы, факты, решения, угрозы, баги.
- AGENT.md (конституция) — как работаем: принципы и правила приёмки.
- **Код — источник истины о факте** (R-17): при расхождении документа с кодом
  главный источник правды о факте — код. Документ, расходящийся с кодом, — это
  баг документа: сначала правим документ, потом работаем. Каждое «сделано/✅»
  подтверждается командой проверки или предъявляемым сценарием; не подтверждено —
  статус снимается.

## Вход в курс (свежая сессия)

Порядок восстановления контекста до первого действия:

0. **Самоотчёт модели (D-19):** сообщи пользователю, на какой модели и variant'е
   реально выполняется сессия (ожидаем `opencode-go/qwen3.8-flash`, variant high).
   Расхождение с D-19 — **СТОП** и отчёт оркестратору.
1. **CONTEXT.md** — суть и статус проекта за 30 секунд.
2. **STATE.md** — факты, решения, баги, «Следующее действие».
3. **ROADMAP.md** — критерии текущего этапа.
4. **AGENT.md** — конституция и правила приёмки.
5. **Базовая линия** до первой правки: `flutter analyze` (0 проблем),
   `flutter test` (все зелёные), `git status` (чисто), `git tag -l` (ожидаемые
   теги на месте). Любое расхождение — СТОП и отчёт.

## Обязательный порядок действий

### Перед каждым шагом
1. **Перечитай `STATE.md`** — актуальный статус; помни: код важнее любого
   документа о фактах (см. иерархию выше)
2. **Перечитай `CONTEXT.md`** — быстрое восстановление сути проекта
3. **`AGENT.md` перечитывай только:**
   - В начале нового этапа
   - Если потерял архитектурный контекст (модульность, D-5 и т.д.)
   - Если столкнулся с нестандартной ситуацией

### При выполнении шага
- Следуй инструкциям буквально
- При обнаружении технической невозможности или архитектурного конфликта —
  **СТОП**, предложи альтернативу, не отклоняйся молча
- При исправлении ошибок в инструкциях — фиксируй обоснование в STATE.md как ФАКТ

### После завершения шага
1. Обнови `STATE.md`: измени статус текущего этапа, добавь запись в журнал изменений
2. Если обнаружена проблема — добавь [УГРОЗУ] в `STATE.md`
3. Если подтвердилась гипотеза — добавь [ФАКТ] в `STATE.md`
4. Если принято решение — добавь [РЕШЕНИЕ] в `STATE.md`
5. Кратко отчитаться перед пользователем: что сделано, что обновлено в STATE.md

## Правила приёмки (уроки аудита 2026-08-31, подробно — в AGENT.md)

1. **Зелёный тест — это утверждение о гарантии, а не гарантия.** Guard-тест
   принят только после внесения нарушения руками и наблюдения красного результата.
   Заглушки `expect(true, isTrue)` запрещены.
2. **Критерий выхода этапа — демонстрируемый сценарий**, а не набор
   файлов/классов/зелёных юнит-тестов.
3. **Чинить на слое причины.** Точечные UI-костыли, которые надо повторять
   в каждом новом месте, запрещены.
4. **Тесты должны ломаться от неправильного поведения:** проверяй путь
   сохранения, гонку, границу — не факт отрисовки виджета.

## Нотификации (D-27)

Отправляй уведомления через скилл `telegram-notify` в трёх точках:
- Завершение пакета: `✅ <пакет>: <итог>, тесты N/N`
- Стоп-гейт: `🛑 СТОП <пакет>: <причина>`
- Ручная приёмка: `👀 <пакет>: зелёный, прогони сценарий: <сценарий>`

Вызов: `./scripts/notify.sh "<сообщение>"`. Сообщения ≤200 символов, без кода и
путей. Fail-silent: при отсутствии конфига скрипт молча exit 0, пакет не падает.
Токен вне репо (`~/.config/dharma/telegram`, 600) — коммитить запрещено.

## Схема классификации (для STATE.md)

### [ГИПОТЕЗА] — H-{номер}
- **H-{номер}**: Описание
  - Статус: [новая|тестируется|подтверждена|опровергнута]
  - Как проверить: план проверки
  - Результат: заполняется после проверки

### [ФАКТ] — F-{номер}
- **F-{номер}**: Описание
  - Источник: откуда известно
  - Дата: когда подтверждено

### [РЕШЕНИЕ] — D-{номер}
- **D-{номер}**: Описание
  - Причина: почему выбрали это
  - Альтернативы: что еще рассматривали
  - Дата: когда принято

### [УГРОЗА] — R-{номер}
- **R-{номер}**: Описание
  - Вероятность: [низкая|средняя|высокая]
  - Влияние: [низкое|среднее|критическое]
  - Митигация: как бороться
  - Статус: [открыта|в работе|закрыта]

Баги живут в секции «БАГИ» STATE.md как **B-{номер}** с полями: описание,
влияние, решение, статус, приоритет.

## Архитектурные принципы (кратко, полная формулировка — AGENT.md)
1. **Модульность** — ядро не знает о конкретных школах; единственное ослабление —
   агрегация схемы БД в `core/db` (D-20); guard-тесты проверяют оба направления
2. **Конфигурируемость** — традиции это JSON-пресеты; пресет обязан
   материализовывать данные (B-3), а не «просто загружаться»
3. **Изоляция данных** — traditionTag из активного пресета, не из литерала
4. **DI только через Riverpod** (D-4 + D-22); service locator запрещён
5. **Миграции** — пошаговые ветки по версиям (D-17); `createAll()` в ветках запрещён
6. **EventBus отложен (D-21)** — междомодульные коммуникации Этапа 5 идут через
   Riverpod-провайдеры и Drift-стримы

## Правила кода

### Запрещено
- Хардкодить названия школ в ядре и в навигации (traditionTag из пресета)
- Создавать циклические зависимости между модулями
- Писать код без тестов
- Использовать глобальные переменные для состояния
- Service locator вместо провайдеров (D-4/D-22)
- `createAll()` в ветках миграций (D-17)
- Заглушки тестов `expect(true, isTrue)` (урок 1)

### Обязательно
- Каждому модулю — свой набор тестов
- Интерфейсы для всех внешних зависимостей
- Документация к публичным API
- Коммиты по Conventional Commits
- Обновление STATE.md каждый шаг; снятие статусов «сделано» при расхождении с кодом

## Коммиты
- `feat(module_name):` — новый функционал
- `fix(module_name):` — исправление бага
- `refactor(module_name):` — рефакторинг
- `test(module_name):` — добавление тестов
- `docs:` — документация
- `chore:` — инфраструктура
