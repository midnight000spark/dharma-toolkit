### H-1: Flutter лучше React Native для модульной архитектуры
- **Статус**: подтверждена
- **Как проверить**: Анализ экосистемы Dart packages для плагинной архитектуры

### H-3: pub.dev tibetan_calendar пригоден только для атрибутов года
- **Статус**: подтверждена с уточнением (5a, 2026-09-01)
- **Как проверить**: Сравнить результаты с tibcal (Python) и date-tibetan (JS) на тест-векторах Лосара 2023-2027
- **Результат**: Уточнение: F-21 описывал v1.x; актуальная v2.0.0 умеет больше —
  атрибуты года совпадают с tibcal/нашим портом (тест), прямая конверсия совпала
  на всех 731 векторах, обратная конверсия и пропущенные/двойные дни есть
  (F-46). НО: реализация на `double` (против D-18), годичная нумерация +127,
  локальная таймзона в выходе, малый трафик — **заменой порту не является**;
  год-атрибуты сверялись тестом, день-уровень — зондом (не тестом).

### H-4: Триггер крахов сессий — кластер бонско-тибетской лексики (модерация провайдера)
- **Статус**: опровергнута (triage-bon-probe, 2026-09-01) — для содержимого запроса в чистом контексте
- **Как проверить**: 15 одноразовых сессий `opencode run -m opencode-go/qwen3.8-flash` вне каталога проекта (без instructions-инъекции AGENT/STATE/CONTEXT), 5 кластеров × 3 попытки: A контроль (Flutter-трекер привычек), B тхеравада (упосатха, фазы Луны), C ньингма (нёндро, мантра, Лосар, Пхугпа), D бон/тибетский (Бон, Чжанчжунг, Bod rGyal, латинские транслитерации g.Yung drung/sTag pa/Zhu), E комбо B+C; задача зонда — выписать термины (грузит и вход, и выход).
- **Результат**: **15/15 PASS.** Кластер D дал полный список терминов 3/3, включая транслитерации; сессия-триаж с бонскими F-47/F-48/D-30 в контексте тоже генерирует без отказов. Реальная картина крашей — сбои провайдера при генерации длинных сообщений на разном содержимом (записана как R-18): APIError «Internal server error» ×8 и пустые payload'ы «Type validation failed: Value: {}» ×3 за 2026-08-31–09-01, контексты в момент смерти 72K–255K токенов. **Чистка бонских упоминаний из кода/docs НЕ выполнена — стоп-гейт сработал** (реестр упоминаний составлен и лежит в журнале, инвентарь не трогаем до уточнения оркестратором).

### R-26: vendor-политики против точных будильников — напоминание может не дойти
- **Описание**: показ напоминаний опирается на `AlarmManager` с точностью `exact` при

  ослабляется не нашим кодом, а политиками вендоров: (а) **Android 14+** —
  `SCHEDULE_EXACT_ALARM` запрещён по умолчанию для новых приложений и может быть
  отозван системой/пользователем, тогда exact-планирование просто не выполняется
  (F-57), остаётся inexact; (б) **Samsung** — лимит порядка 500 будильников в
  `AlarmManager` на приложение (F-55); (в) **OEM-killers** (Xiaomi/Huawei и др.)
  вырезают фоновые будильники и автозапуск приложений — плагином не решается
  (F-55, внешний ориентир dontkillmyapp.com). Итог: на части устройств плановое
  напоминание не приходит, хотя план корректен и pending виден системе.
- **Вероятность**: высокая (политики Android 14+ действуют по умолчанию, OEM-ограничения массовы)
- **Влияние**: среднее (FR-EVT-2 выполняется «с честной точностью»; в особый день
  пользователь может не получить напоминание — обещание ослаблено, но не нарушено молча)
- **Митигация**: честный inexact-fallback уже в D-36 (не врём о точности, если
  разрешения нет); потолок 64 pending и своя полоса id ограничивают давление на
  лимиты; отказ платформы не молчит (деградация в лог, F-57); на Этапе 8 — подсказка
