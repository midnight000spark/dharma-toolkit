### R-26: vendor-политики против точных будильников — напоминание может не дойти
- **Описание**: показ напоминаний опирается на `AlarmManager` с точностью `exact` при
  выданном `SCHEDULE_EXACT_ALARM` (D-36, F-57). На реальных прошивках это обещание
  ослабляется не нашим кодом, а политиками вендоров: (а) **Android 14+** —

### B-25: «Попробовать снова» при штатном отказе старта остаётся без обратной связи (найден живым прогоном fix1-accept)
- **Описание**: строка `retry-failure` («Повторная попытка не удалась (попытка N)»)
  рендерится только если `widget.onRetry` **бросает**. В composition root
  `onRetry: start`, а `start` → `runStartupCycle`, который по контракту отказ
  наружу не выпускает: монтирует восстановление и возвращает
  `MountedRoot.recovery` (`lib/core/recovery/startup.dart:114-118`). В главном
  сценарии (битая база) `catch` в `_run` не срабатывает → `_attempts` не растёт,
  строки на экране нет.
- **Доказательство** (release APK, API 35, 2026-09-21): заголовок БД забит
  мусором → экран восстановления → два тапа «Попробовать снова»: в `logcat` три
  прогона зонда в одном pid, на экране узлов `Повторная попытка не удалась…` нет.
- **Почему тесты зелёные**: `recovery_screen_test.dart` подаёт `onRetry`, который
  бросает сам, — проверяется виджет, а не связка «виджет ↔ реальный цикл старта»
  (урок «гард должен стоять на стыке»).
- **Влияние**: средний — тот самый момент, где пользователь решает, стирать ли
  данные. Не потеря данных, не падение: отсутствие сигнала «попытка не удалась».
- **Решение**: не принято (стоп-гейт приёмки — находку не чинить молча).
  Кандидаты: (а) `_run` сверяет возвращаемый `MountedRoot`, а не ждёт броска;
  (б) `runStartupCycle` пробрасывает отказ вторым значением кортежа; (в) счётчик
  попыток поднимается на уровень монтируемого корня.
- **Статус**: открыт · **Приоритет**: средний
